# 视频分析并发与缓存

## 模块职责

`VideoAnalysisService` 负责来源授权、区间选择、缓存、任务合并与流程编排。`VisionModelPort` 和 `TranscriptionPort` 提供独立模型接口，当前由 `VideoModelClient` 实现 compatible / MiniMax 协议及 HTTP 请求。已有超时、取消、响应大小限制和任务模型预算仍在供应商请求边界生效。

`FrameComposer` 生成带采样时间戳的拼图，解码前读取尺寸并拒绝超过 1280×1280 的输入，限制帧数量和 Base64 长度；每帧间检查取消，图形资源始终释放。`VideoFactsValidator` 将供应商输出校验为绑定来源版本、区间与采样锚点的证据。

## 缓存锁与清理

数据库查询、JSON 解析与写入不再持有缓存对象的整对象锁。内存模式使用 Caffeine 管理容量、写后过期和并发访问，不再手动维护 Map 锁。慢数据库请求不会阻塞其他 key 的缓存访问。

读到不符合 Facts 格式的缓存 JSON 时，清理语句同时匹配 key 和原 JSON 内容，避免删除并发刷新后的有效记录。数据库 TTL 仍为一天，内存 TTL 仍为一小时；缓存过期行仍按原写入路径分批清理。

缓存 key 的各字段分别哈希后组合，避免租户与用户字段中的分隔符导致边界歧义。包含租户、用户、videoId、来源版本、区间、关注点、供应商端点与模型配置。使用新的 `video-cache-v2` key，旧缓存不迁移，会自然过期；首次分析可能重新调用模型。

## 同一分析请求的合并

同一实例内，同 key 缓存未命中请求通过 `VideoAnalysisFlights` 和 Caffeine 原子登记共享一次在途计算。发起者使用原工作线程和自己的任务预算，等待者不创建新线程、不重复提取媒体或调用模型、不额外占用模型调用额度。选出发起者后再次查缓存，避免缓存写入与在途登记之间的时间窗口造成重复调用。

每个请求在查缓存或加入在途计算前都独立查询授权来源。未命中的请求拿到结果后，还会使用自己的身份重新查询授权来源，拒绝撤权或来源版本变化后的交付。工具仍为每个运行任务独立登记证据 ID，不共享其他任务的证据 ID。

等待者每次最多等待 50ms，再检查自己的取消与 deadline。等待者取消、线程中断或超时不会取消发起者与其他等待者。发起者由于自身取消、超时或预算失败退出时，仍有额度且未超时的等待者可重新竞争执行；普通供应商错误由当前等待者共同接收，失败结果不进入缓存。在途项在成功、异常或 Error 后都会移除，最多保留 128 个不同 key。

在途计算在发起者线程执行，因此供应商调用、Token 与细节 Trace 归属于发起者。等待者 Span 使用 `video.shared_wait` 与 `video.shared_wait_ms` 标记共享等待，不能把其零模型消耗解释为独立调用过供应商。缓存命中继续使用 `video.cache_hit`。

## 验证与边界

`VideoAnalysisFlightsTest` 覆盖同 key 共享、不同 key 并发、独立取消、线程中断、等待 deadline、发起者预算失败后的重试及失败清理。`VideoAnalysisConcurrencyTest` 覆盖实际服务中的单次 Token 扣账、各调用者再次授权，以及等待期间撤权。`VideoContentCacheTest` 覆盖慢 SQL 并发和带原内容条件的损坏缓存清理；`FrameComposerTest` 覆盖拼图与畸形/超尺寸输入。原供应商协议、证据锚点、私有报告与模型预算测试保持运行。

合并只在单实例进程内生效，不是分布式锁。数据库并发测试使用阻塞 JDBC fixture，不代表真实 MySQL 容量验收；没有调用收费视频模型。等待者仍占用现有工具工作线程，工作池与背压隔离属于下一步并发资源治理。
