# 产品与技术迭代方案

日期：2026-10-26。主用户暂定为天幕创作者，后续根据真实使用反馈调整。

## 产品方向

做一个能把视频内容、观众反馈和可核对证据放在一起的创作者复盘助手。优先完成三个任务：查询已授权数据、定位需要查看的片段、形成有依据且可以验证的改进建议。

一条完整交付应包含：观察到了什么、证据来自哪里、覆盖了哪些素材、还有什么不能确定、建议采取什么行动。HTML 只是展示载体；可信的分析与复盘闭环才是能力。

当前最多12帧的视频概览和每发送时间箱最早4条、合计最多48条弹幕片段，都有明显覆盖边界。它们不能直接支持逐帧理解、全量情绪占比、观众流失或确定因果。播放时间、弹幕发送时间和视频发布时间需要分别建模；共享 videoId 不表示视频与直播的分析口径相同。

## 迭代方式

每轮只扩大一个主要能力边界：先固定样例和预期，再实现，再对相同样例回归。沿用现有 Maven/JUnit、HTTP/SSE 冒烟、前端 Node 测试和 ArchUnit，不另造评测服务或工作流平台。

当前工作区累积了多轮架构修改。第一步先把它们作为明确的候选基线，按职责整理可评审的改动；未完成验收前不同时扩展新业务、升级模型框架与修改认证协议。

## 里程碑

| 迭代 | 目标与主要交付 | 验收条件 | 依赖 |
| --- | --- | --- | --- |
| 1：评测与发布基线 | 整理当前改动；固定首批24条业务场景；给测试素材建立版本/数据快照；记录回答、工具、证据、耗时、调用次数和 usage 状态 | 工程回归可复现；真实样例有人工或 SQL 对照；工程通过、语义正确、未评测三种结果明确区分 | 当前源码与构建；经授权的测试素材用于真实质量标注 |
| 2：时间轴数据与候选片段 | 明确 createdAt/playbackMs/publishedAt；增加全量播放位置的弹幕统计；记录未知位置数量；让证据引用可定位到具体播放片段 | 播放位置统计与 SQL 一致；缺失位置不参与对齐；发送日期峰值不能被解释成播放高能点 | 迭代1；业务侧可靠的播放位置数据 |
| 3：按问题取证的视频理解 | 概览后按需细查；在预算内选择候选片段；带时间戳的转写/镜头信息按来源版本复用；逐步把重复预处理放到异步作业 | 在固定问题集上，关键事件定位和证据支持率优于基线；未覆盖片段明确披露；缓存/任务不跨权限或版本复用 | 迭代2；具备标注的片段问题 |
| 4：比较与复盘 | 同视频的不同时段、本人视频之间的比较；固定同口径条件；区分可见事实、观众表达和关联推测；形成少量具体行动建议 | 差异可由证据复算；明确发布时间/采样覆盖等差异；没有曝光或观看数据时不输出互动率、留存率或流失结论 | 迭代3；可比数据与业务指标定义 |
| 5：业务记忆与行动反馈 | 保存用户确认的术语/纠正、复盘结论与采用的行动；用户主动回看时获取同口径后续数据，评估观察是否变化 | 记忆有来源、作用域、版本和删除能力；用户纠正不会直接覆盖原始事实；变化不被宣称为行动的因果效果 | 迭代4；真实用户持续使用 |
| 6：按使用证据扩容 | 根据队列、延迟、成本和失败类型决定异步批处理、模型分工或多实例租约；再评估 SDK 替换 | 有负载基线；故障下执行归属、取消与终态明确；每项复杂度能对应具体瓶颈或质量收益 | 前几轮产生的业务和运行数据 |

不预先给工期或主观准确率承诺。迭代1取得基线后，再确定可接受的延迟、成本与答案质量门槛。

## 第一轮的具体任务

1. 当前架构候选基线：Agent 与业务后端构建、前端测试/构建、HTTP/SSE 冒烟分别保留结果；明确外部集成跳过项和发布扫描已有告警。
2. 使用 `../eval/scenarios.json` 的24条场景建立验收清单。初始状态均为 draft，不能算作已经通过的真实模型评测。
3. 每条真实样例绑定测试账号作用域、素材版本、数据快照和证据锚点。确定性数字用 SQL 或固定 fixture 对照；视频内容与建议用人工标注。
4. 运行时记录具体模型与 Prompt/Skill 版本；默认使用既有免 Key fixture。真实模型调用显式启用并受预算控制，不自动调用付费模型。
5. 先分析失败原因，再选择下一条优化：条件解析失败、工具取证不足、覆盖范围不足、模型推理错误和交付表达错误不能混在一个总分中。

## 评测维度

| 维度 | 判断方式 |
| --- | --- |
| 事实和数字 | 与 SQL/快照一致；统计口径不变化 |
| 时间定位 | 是否引用了对应片段；允许误差由每条标注定义 |
| 证据支持 | 结论能否由已提供证据支持，而非只检查引用 ID 是否存在 |
| 边界诚实 | 对未知播放位置、采样覆盖和缺失音频是否正确处理 |
| 任务完成 | 用户要的查询/定位/报告是否完成；澄清是否必要 |
| 运行成本 | 端到端耗时、排队耗时、模型次数、完整/缺失 usage、缓存命中 |
| 使用价值 | 用户能否据此定位问题、节省复盘时间、形成具体行动；以真实试用反馈记录 |

越权、伪造证据、任务间数据串用等属于阻断项，不能被平均质量分掩盖。模型评审可以辅助，但不能作为事实与权限的唯一裁判。

## 技术取舍

- 固定统计、授权、证据登记与产物持久化走确定性流程；只有不确定的候选片段选择、解释和补充取证交给受限 Agent 决策。
- 一般聊天和确定性查询不应无条件支付所有预处理分支成本。是否合并/移除意图或情绪调用，应通过第一轮的路由质量与耗时对照决定。
- 语义检索在视频片段/转写确实需要检索时再引入，先复用现有数据库和搜索设施；不先建全能知识库。
- 业务记忆与聊天记录分开；视频事实、用户确认和分析假设有不同状态，不以增加历史上下文代替业务记忆。
- 现阶段不优先多 Agent、全自动发布/删改内容、跨平台数据平台或完整框架迁移。现有身份仅覆盖本人视频，平台运营角色需要单独的权限和任务设计。

取证与工作流复杂度的取舍参考 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)；视频评测维度参考 [Video-MME](https://video-mme.github.io/home_page.html) 和 [LongVideoBench](https://longvideobench.github.io/index.html)。这些资料不替代天幕自己的业务问题集和验收结果。
