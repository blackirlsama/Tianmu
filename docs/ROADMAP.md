## Q02 第一批实施记录（2026-10-31）

- `CurrentUser` 提供可复用的当前用户入口：只读取拦截器写入的身份属性，不从请求体或客户端字段推断身份。JWT 拦截器在签名与 Redis 在线会话匹配后设置身份，拒绝无效、溢出用户 ID；公开接口不建立未经验证的身份。未改变现有 raw token / Bearer token 兼容方式。
- 点赞按可信身份执行；旧请求的 userId 字段可保留或省略，但指定其他用户会被拒绝，且拒绝发生在查数和限流之前。
- 取消点赞先加载真实记录，校验拥有者及视频；删除带记录 ID、拥有者、视频条件，只有实际删除成功才更新统计。统计使用记录视频，且只允许正计数扣减；更新失败抛出异常，交由已有事务回滚。
- 回归覆盖身份冒用、无身份、错视频、他人记录、无记录、重复删除不重复计数、统计失败、正常创建/取消，以及凭证撤销、更换、非法主体与公开接口身份隔离。
- 当前测试为服务与拦截器回归；模拟“另一请求已删除”的结果验证计数门槛，不等价于真实数据库并发测试。数据库回滚与并发取消仍需在隔离 MySQL 上验证。

## Q01 实施记录（2026-10-31，本地修复）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 只提供他人的 userId，且对方在线 | 可以通过在线记录检查，冒充他人发送 | 每条消息验证 JWT 签名、有效期与 Redis 当前会话；缺失/失效凭证不会入队或广播 |
| 有效凭证却指定其他 userId，或连接视频 X 却指定视频 Y | 可能广播到 X 却以 Y 的数据入库 | 身份来自凭证，视频来自连接房间；客户端提供的身份/视频必须一致，不一致拒绝 |
| 连接后退出登录或在别处重新登录 | 只要原用户仍存在在线记录，旧连接仍可能发送 | 每次发送重新核对当前凭证，已撤销或被替换的 Token 无法继续发送 |
| 畸形 JSON、非法房间、内容超长、负数播放时间 | 缺少明确、统一的入口约束 | 路径仅接受正数 Long 视频 ID；帧限 16 KiB；拒绝重复 JSON 字段、尾随 JSON、空白/超过 255 UTF-16 单元的正文、非有限或负数时间及非法颜色 |
| 删除/下架/未发布的视频 | 未在 WebSocket 发送边界检查视频可用性 | 发送前检查视频未删除且 status=2（与公开媒体读取口径一致） |
| 入队失败或原始消息包含凭据/伪造时间 | 原消息调试输出，客户端字段与服务端字段混在一起 | 仅投影业务字段入队，身份/视频/ID/时间由服务端确定；不输出帧或供应商异常正文，MQ 发送成功后才广播；失败返回独立错误消息 |

- `SessionAuthentication` 统一 JWT 与在线会话规则，HTTP 拦截器和 WebSocket 入口复用；Agent bridge 的业务账号与视频权限检查保持原有边界。
- 游客仍可接收公开弹幕。浏览器不能给 WebSocket 设置任意 Authorization 头，前端改为在私有发送帧中携带当前凭证，凭证不进入连接 URL、MQ 或广播；无凭证的旧协议发送请求不会回退放行。
- 新增通用错误 type=4，与登录失效 type=3 分开，参数/队列错误不再被当成退出登录；前端检查连接已打开，发送前清除上次成功标记。标准 WebSocket Ping/Pong 替代文本心跳。

- 调研依据：[goim 房间缓冲与时间/数量触发实现](https://github.com/Terry-Mao/goim/blob/master/internal/job/room.go)、[Netty ChannelGroup 批量写入与连接生命周期](https://netty.io/4.1/api/io/netty/channel/group/ChannelGroup.html)。仅借鉴房间聚合模式，本次不增加消息分发中间件、压缩、跨节点广播或慢连接降级。
- 新增 `RoomBatchBroadcaster`，统一管理房间成员和待广播批次。默认从第一条消息起等待最多 100 ms，达到 50 条或 16 KiB 提前发送；JSON 外壳、逗号和 UTF-8 正文都计入字节限制。时间、条数、字节阈值可通过业务环境变量配置，配置边界见前端 README 与 `.env.example`。
- 每个房间仅保留一个受条数/字节限制的待发送批次及一个定时器；房间内部追加/发送串行化。达到阈值立即发送，不另外堆积无界的待广播任务。取消的定时任务及时从调度器队列移除，过期回调不能影响下一批。
- 房间清空时取消计时并释放待发送数据；已入队的业务弹幕仍走原持久化链路。服务关闭时尝试发出待广播批次、关闭房间连接，再依序停止业务与 IO 线程；不承诺所有关闭中的客户端都已接收消息。
- 新协议 `type=5, data=[...]`，每条弹幕仍保留独立 ID 和播放时间；MQ 入队和消费者入库仍逐条执行，批次仅作用于实时广播。人数、认证错误和业务错误消息继续立即发送。
- 前端同时兼容旧单条 `type=2` 与新批次 `type=5`，一次处理混合作者的消息；自己的回显继续驱动原发送标记，他人的消息批量追加播放器。未引入独立 ACK，未修改历史查询、缓存完整性、历史/增量统一去重或按播放区间订阅。
- 回归新增后端 9 项、前端 4 项；覆盖时间/数量/字节触发、UTF-8 大小、房间隔离、空房间释放、过期定时器、关闭、顺序与并发不重不漏。确定性用例验证 100 条消息按 10 条/批输出 10 帧，这是批次行为验证，不是线上容量压测。
- 最终验证：业务模块 `mvn -B -ntp verify` 构建成功，93 项中通过 74、外部环境测试跳过 19，失败/错误 0；前端 29/29 测试及生产构建通过；发布规则 4/4、部署静态检查 11/11、发布检查与差异格式检查通过。真实本地 Socket 测试使用新批次协议，关闭流程未再出现线程池提前终止异常。尚未推送或部署；发布需前后端配套，新前端可先行兼容旧后端，旧页面需刷新。
